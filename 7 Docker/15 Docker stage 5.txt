Load Balancing Project with Docker-Compose
==========================================
📌 Nginx Load Balancer - Dockerfile Setup
--------------------------------------

                     Container     --- Container1- backend1
User --------> NGinx Load Balancer --- Container2- backend2
                                   --- Container3- backend3

We need image for Nginx LB, for that we need Dockerfile, and we take other account dockerhub image for backend

This Dockerfile will set up Nginx as a Load Balancer for multiple backend services inside Docker.

Step 1: Create a Dockerfile to generate image for Nginx LB
Step 2: Create nginx.conf locally and copy to containers through docker-compose
Step 3: Create docker-compose file to create containers in one shot

1️. Create the Dockerfile
--------------------------

vi Dockerfile

# Use the official Nginx image
  FROM nginx:latest

# Remove default config and copy custom nginx.conf
RUN rm /etc/nginx/conf.d/default.conf
COPY nginx.conf /etc/nginx/conf.d/

# Expose port 80
EXPOSE 80

# Start Nginx
CMD ["nginx", "-g", "daemon off;"]



is used to keep Nginx running in the foreground when running inside a Docker container.
- Why is daemon off; Needed?
By default, Nginx runs as a background (daemon) process.
In a Docker container, the main process must stay in the foreground.
If Nginx runs as a daemon, Docker thinks the container has exited.
Setting "daemon off;" prevents it from running in the background, keeping the container alive

2️. Create the Nginx Load Balancer Config (nginx.conf)
-------------------------------------------------------

vi nginx.conf
i

# Define the upstream backend servers
upstream backend {
    server backend1:5000;
    server backend2:5001;
    server backend3:5002;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Docker Restart Policies
=======================
Docker Restart Policies control what Docker should do with a container, if it stops, crashes, or if the Docker daemon or host restarts.

This is commonly used in production to keep important services like Nginx, MySQL, Jenkins, and Prometheus running automatically.

Why Restart Policies?
---------------------
Imagine you have an Nginx container running.

Client is talking to --> Nginx Container

Suddenly, Application crashes or Docker daemon restarts or Server reboots

Without a restart policy: Container is Stopped. The application remains unavailable until someone manually starts it.

With a restart policy: Container Stops --> Docker Automatically Starts It. This improves application availability.

Types of Restart Policies
---------  -----------------
Docker supports four restart policies:
|----------------|-------------------------------------------------------------------|
| Policy         | Description                                                       |
| -------------- | ----------------------------------------------------------------- |
| no             | Never restart the container (default)                             |
| on-failure     | Restart only if the container exits with a non-zero exit code     |
| always         | Always restart the container whenever it stops or Docker restarts |
| unless-stopped | Restart automatically unless the user explicitly stopped it       |
|----------------|-------------------------------------------------------------------|

1. no (Default)
----------------
Docker does nothing. If the container stops, it remains stopped.

Run Container

-- docker run -d --name web nginx

or explicitly

-- docker run -d --restart=no --name web nginx

-- docker inspect web | grep RestartPolicy -A 3       -- [Output= Name : no]

-- docker stop web [Containers just Stopped with Exit 0]

-- docker ps -a

Docker will never restart it automatically.

2. on-failure
--------------
Docker restarts the container only if

Application exits with an error. Exit Code 0 means Success. Exit Code 1 means Failure

-- docker run -itd --name cont1 --restart=on-failure ubuntu false      --[false: always return exit code 1, docker see application failed and restart]

-- docker run -itd --name cont2 --restart=on-failure:5 ubuntu false     --[Docker tries 5 times, after 5 times containers stops]

-- docker rm -f cont1
-- docker rm -f web

When to Use ?

Batch jobs
Cron jobs
Data processing
Scripts


always
-------
This is the most commonly used restart policy.

Docker restarts the container

If application crashes
If Docker daemon restarts
If server reboots
If container exits

-- docker run -itd --restart=always --name cont3 nginx

-- docker inspect cont3 | grep RestartPolicy -A 3      --[Restart Policy Name: always]

Now stop the container

-- docker stop cont3

Container stops. If the Docker daemon or the host is restarted, Docker will start the container again because the policy is always.

-- systemctl restart docker [Restart the Daemon]

-- docker ps -a    -- [Now see cont3 is up !!]
-- docker rm -f cont3

Production Use

Jenkins
Nginx
Apache
MySQL
Redis
Prometheus
Grafana

unless-stopped
--------------
Similar to "always" except If you manually stop the container, Docker remembers your choice.

-- docker run -d --restart=unless-stopped --name cont4 nginx

-- docker inspect cont3 | grep RestartPolicy -A 3      --[Restart Policy Name: unless-stopped]

-- docker stop cont4

Now reboot Docker or the host. Container remains stopped. Docker respects your manual stop.

| Policy         |            Crash           | Docker Restart | Server Reboot |                 Manual Stop                |
| -------------- | :------------------------: | :------------: | :-----------: | :----------------------------------------: |
| no             |            ❌ No            |      ❌ No      |      ❌ No     |                Stays stopped               |
| on-failure     | ✅ Yes (non-zero exit code) |      ❌ No      |      ❌ No     |                Stays stopped               |
| always         |            ✅ Yes           |      ✅ Yes     |     ✅ Yes     |   Starts again after Docker/host restart   |
| unless-stopped |            ✅ Yes           |      ✅ Yes     |     ✅ Yes     | **Remains stopped** until manually started |


Best Practices
--------------
Use always for services that must always be available (for example, reverse proxies or monitoring agents).
Use unless-stopped for long-running applications that administrators may intentionally stop for maintenance.
Use on-failure for jobs or scripts that should retry only after failures.
Leave the default no for containers you intend to start manually.

Interview Questions
---------------------
1. What is a Docker restart policy?
-------------------------------------
A restart policy tells Docker whether and when to automatically restart a container after it exits, crashes, or after Docker/the host restarts.

2. What is the default restart policy?
-------------------------------------
no

Docker does not automatically restart the container.

3. What is the difference between always and unless-stopped?
----------------------------------------------------------
always restarts the container even if it was manually stopped, once the Docker daemon or host restarts.
unless-stopped also restarts automatically after crashes or reboots, but not if the container was manually stopped.

4. What is on-failure?
------------------------

It restarts the container only when the application exits with a non-zero exit code, indicating failure.

5. How do you change the restart policy of an existing container?
----------------------------------------------------------------
docker update --restart=unless-stopped container_name

6. How do you check a container's restart policy?
-----------------------------------------------
docker inspect -f '{{ .HostConfig.RestartPolicy.Name }}' container_name

7. Which restart policy is commonly used in production?
----------------------------------------------------------
always for infrastructure services that should always come back automatically.
unless-stopped for most long-running applications, because it respects intentional manual stops.
