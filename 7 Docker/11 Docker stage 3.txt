Image Layers
--------------

A Docker Image is not a single file.

It is made up of multiple layers.

Each Dockerfile instruction generally creates a new layer.

One of Docker's biggest advantages is Layered Architecture.

Each instruction generally creates a new read-only layer.

Example:
--------
vi Dockerfile

FROM ubuntu
RUN apt update
RUN apt install nginx -y
COPY index.html /var/www/html
CMD ["nginx","-g","daemon off;"]


Layer 5   CMD

Layer 4   COPY index.html

Layer 3   RUN apt install nginx

Layer 2   RUN apt update

Layer 1   FROM Ubuntu


Writable Layer
    ↓
Read Only Layer 5
    ↓
Read Only Layer 4
    ↓
Read Only Layer 3
    ↓
Read Only Layer 2
    ↓
Read Only Layer 1


The container adds one writable layer on top.


-- docker history imagename:tag [It shows all the image layer history]

Every RUN creates another image layer. [To reduce the image creation time or size, use less layers]

Docker caches every successfully built layer.

Cache Invalidation
---------------------
Docker rebuilds all layers after a changed layer.

Disable Cache
-------------
Sometimes we want a fresh build.

-- docker build --no-cache -t app:v1 .

-- docker build --progress=plain .  [Build Progress, detailed logs]


Image Optimization
--------------------
A Docker image should be

Small
Secure
Fast
Optimization 1 : Use smaller base images. Instead of ubuntu, use alpine or python:3.12-slim
Optimization 2 : Combine RUN commands. Every RUN command create layers. use Single Layer

BAD
---
RUN apt update
RUN apt install nginx -y
RUN apt install curl -y

Good
----
RUN apt update && \
    apt install -y nginx curl && \
    apt clean && \
    rm -rf /var/lib/apt/lists/*

Optimization 3: Use .dockerignore , avoid copying .git, logs, target, node_modules etc
Optimization 4: Use COPY instead of ADD
Optimization 5: Use Multi-stage Builds
Optimization 6: Avoid latest tag. Always use version tags to have Predictable builds.
Optimization 8: Clean Package Cache
RUN apt update && \
    apt install -y nginx && \
    apt clean && \
    rm -rf /var/lib/apt/lists/*


Union File System (UnionFS)
---------------------------
One of Docker's most powerful features is the Union File System.

It combines multiple read-only layers into a single unified filesystem that the container sees.

Docker merges all these layers into one view.

The container does not see separate layers. It sees as one filesystem.

Read-only Layers
-----------------
All image layers are read-only.

When you run a container, Docker creates a writable layer on top.
Any file changes happen only in the writable container layer.

1. What happens during docker build?
------------------------------------
Docker reads the Dockerfile from top to bottom, executes each instruction, creates image layers, caches them when possible, and produces a Docker image.

2. What is a Docker image layer?
--------------------------------
An image layer is a read-only filesystem layer created by most Dockerfile instructions. Docker stacks these layers to form the final image.

3. Why is Docker caching useful?
--------------------------------
Caching avoids rebuilding unchanged layers, making subsequent builds much faster.

4. What causes Docker cache invalidation?
-----------------------------------------
If a Dockerfile instruction changes, or the files used by that instruction change (for example, a COPY source), Docker rebuilds that layer and all following layers.

5. Why should COPY requirements.txt come before COPY . .?
---------------------------------------------------------
Because application code changes more frequently than dependencies. Copying and installing dependencies first allows Docker to reuse the cached dependency layer, significantly reducing build times.

6. How do you optimize a Docker image?
--------------------------------------
Use a smaller base image (slim or alpine where appropriate)
Combine related RUN commands
Use .dockerignore
Prefer COPY over ADD
Remove package caches and temporary files.
Use multi-stage builds
Run as a non-root user
Pin image versions instead of using latest

1. What is a Docker Image?
---------------------------
A Docker Image is a read-only template containing the application, runtime, dependencies, libraries, and configuration needed to create containers.

2. What is the difference between an Image and a Container?
----------------------------------------------------------
An image is a static, read-only blueprint. A container is a running, writable instance created from that image.

3. What are Image Layers?
-----------------------
Image layers are read-only filesystem layers created by Dockerfile instructions. Docker reuses shared layers across images to save storage and speed up builds.

4. What is the Union File System?
---------------------------------
The Union File System combines multiple image layers into a single unified filesystem view, allowing containers to see one coherent directory structure while Docker stores the layers separately.

5. What is a Base Image?
------------------------
A base image is the starting image specified with the FROM instruction in a Dockerfile. All subsequent layers are built on top of it.

6. What is an Official Image?
------------------------------
An official image is an image published or maintained by the upstream project through Docker Hub. Examples include nginx, ubuntu, mysql, and python.

7. What is a Custom Image?
---------------------------
A custom image is an image built by a user or organization using a Dockerfile to package their own application and configuration.

8. What happens if you delete a container?
--------------------------------------------
Only the container and its writable layer are removed. The underlying image remains on the system unless you explicitly remove it using docker rmi.



ENTRYPOINT
-----------
Defines the main executable of the container.

Unlike CMD, it cannot be easily replaced.

ENTRYPOINT → "What application should always run?"
CMD → "What are the default arguments for that application?"

vi Dockerfile

FROM ubuntu:24.04
CMD ["echo", "Hello from CMD"]

docker build -t cmd-demo .
docker run cmd-demo  [Output is: Hello from CMD]
Override CMD
------------
docker run cmd-demo date  [It prints date, Docker ignored previous CMD]

So CMD is easily replaced.


Only ENTRYPOINT
---------------

vi Dockerfile

FROM ubuntu:24.04
ENTRYPOINT ["echo","Hello from ENTRYPOINT"]


docker build -t entry-demo .
docker run entry-demo [Output: Hello from ENTRYPOINT]
Now run
--------
docker run entry-demo date [Output: Hello from ENTRYPOINT date]

Why? Docker actually executed, echo "Hello from ENTRYPOINT" date

The command after the image name became an argument, not a replacement.

ENTRYPOINT cannot be overridden just by passing another command.


ENTRYPOINT + CMD (Most Common)
----------------------------

vi Dockerfile

FROM ubuntu:24.04
ENTRYPOINT ["echo"]
CMD ["Hello Docker"]

docker build -t both-demo .
docker run both-demo [Output: Hello Docker. Docker internally executes echo "Hello Docker"]
Override CMD
-------------
docker run both-demo "DNA by Balaji"  [Output: DNA by Balaji, Docker internally executes echo "DNA by Balaji"]

Notice: ENTRYPOINT stayed, Only CMD changed.

ENTRYPOINT is fixed.



Example: Just theory
----------

FROM python:3.12

WORKDIR /app
COPY . .

ENTRYPOINT ["python", "app.py"]

Running: "docker run myapp" will execute "python app.py --port 8080"

ONBUILD
-------
No need to run***
Creates a trigger that executes when another image uses this image as its base.
Don't execute this instruction now. Execute it later when someone uses this image as a base image.

vi Dockerfile
FROM ubuntu

ONBUILD COPY . /app

Mostly used for creating reusable base images.


1. What is a Dockerfile?
----------------------
A Dockerfile is a text file containing instructions that Docker follows to build a container image automatically and consistently.

2. What is the difference between CMD and ENTRYPOINT?
---------------------------------------------------
CMD specifies the default command or default arguments and can be overridden when starting the container.
ENTRYPOINT defines the main executable that always runs. Command-line arguments are appended to it unless it is explicitly overridden with --entrypoint.

3. What is the difference between COPY and ADD?
----------------------------------------------
COPY copies files and directories from the build context into the image.
ADD can also automatically extract local tar archives and supports additional source types. For most use cases, COPY is recommended because it is simpler and more predictable.

4. What is the difference between ENV and ARG?
---------------------------------------------
ARG is available only during the image build process.
ENV sets environment variables that are available both during image creation (after they are defined) and when the container runs.

5. What is the purpose of EXPOSE?
-------------------------------
EXPOSE documents the port on which the application inside the container listens. It does not make the port accessible from the host; publishing requires the -p or --publish option when running the container.
