=============================
Distroless images are minimal container images that contain only the necessary runtime dependencies for an application—without including an entire Linux distribution (like Debian or Ubuntu). This makes them:

✅ Smaller (Reduced attack surface & faster deployment)
✅ More Secure (Fewer vulnerabilities, no package managers, shells, or extra tools)
✅ Efficient (Uses fewer resources)

Implementing Multi-Stage Builds:
============================================
- A multi-stage build utilizes multiple FROM statements within a single Dockerfile, each initiating a new build stage.
- Artifacts from previous stages can be selectively copied into subsequent ones.

- A multi-stage Docker build uses multiple FROM instructions in a single Dockerfile.
- The first stage builds your application (using build tools like Maven or Gradle), and the second stage copies only the final artifact into a smaller runtime image.
- This produces smaller, more secure images.

-- mkdir docker
-- cd docker
-- yum install git -y
-- yum install tree -y
-- git clone https://github.com/sugganabalaji/java-project-maven-new.git

vi Dockerfile

# ---------- Stage 1 : Build ----------
FROM maven:3.9.9-eclipse-temurin-17 AS build

WORKDIR /app

# Copy project files
COPY . .

# Build the WAR file
RUN mvn clean package -DskipTests

# ---------- Stage 2 : Runtime ----------
FROM tomcat:10.1-jdk17-temurin

# Remove default applications
RUN rm -rf /usr/local/tomcat/webapps/*

# Copy the generated WAR from the build stage
COPY --from=build /app/target/*.war /usr/local/tomcat/webapps/ROOT.war

EXPOSE 8080

CMD ["catalina.sh", "run"]

Q1. What is a multi-stage build?
--------------------------------
A Docker feature that uses multiple FROM instructions to separate the build environment from the runtime environment, creating smaller and more secure images.

Q2. Why use COPY --from?
------------------------
To copy only the required build artifacts (such as a JAR, WAR, or binary) from one stage to another without including build tools or source code.

Q3. What are the advantages multi-stage build ?
-----------------------------------------------
Smaller image size
Faster downloads and deployments
Improved security
Cleaner runtime image
Easier maintenance

This is the recommended approach for Java, Node.js, Go, .NET, and many other application types.

Visual Flow
=============

Docker Client → Docker Daemon → Container Runtime → Containers


docker run nginx
        ↓
Docker Client [CLI (docker run, docker build, Sends REST API calls]
        ↓
Docker Daemon (dockerd) [Brain of Docker, Builds images, runs containers, manages networks & volumes]
        ↓
containerd  [Modern Docker uses Container Runtime, containerd and runc]
        ↓
      runc
        ↓
Linux Kernel (namespaces + cgroups)
        ↓
Container running



dockerd → containerd → runc → container process


Docker follows a client-server architecture.
When we run a command like docker run, the Docker client sends a request to the Docker daemon (dockerd) via REST API.
Internally, the daemon uses container runtimes like 'containerd' and 'runc'.
containerd manages the container lifecycle like manager (pulling images, storage, networking).
'runc' is the low-level runtime that actually creates and starts the container process, works directly with Linux kernel, namespaces and cgroups.

Isolation & Resource Management
==================================
Docker containers are not VMs — they use Linux kernel features:

Namespaces → provide isolation
    PID (process isolation)
    NET (network isolation)
    MNT (filesystem isolation)

cgroups (control groups) → manage resource limits
CPU
Memory
I/O

Namespaces provide isolation (PID, network, mount, etc.), ensuring containers don’t see each other’s resources.

cgroups control resource limits like CPU and memory, preventing one container from consuming all system resources.




Layered Filesystem
===================
Docker images use a layered filesystem (UnionFS):

Each image is made of multiple read-only layers
When a container runs, Docker adds a writable layer on top
Uses copy-on-write mechanism

👉 Benefits:
    Faster builds
    Image reuse
    Efficient storage

“Docker uses containerd and runc to run containers as isolated processes using namespaces and cgroups, and leverages a layered filesystem for efficient image management.”

Docker uses Union File System
Docker image is made of multiple layers:

Layers:
Layer 1: OS (Ubuntu)

Reusability, Faster builds , Less storage

What is Copy-on-Write (CoW) ?
=============================

Files are not copied until modified

Image layer: file.txt = "Hello"  , Container starts → no copy yet
When you modify: file.txt = "Hello World", Docker Copies file to writable layer and Modifies there

Copy-on-write means that Docker does not duplicate files from image layers until they are modified.
When a change occurs, the file is copied to the container’s writable layer and modified there, improving efficiency.

RUN npm install

COPY . .
RUN npm run build

# Stage 2: Serve
FROM nginx:alpine

It uses two stages:

Build stage (Node.js)
Runtime stage (Nginx)

Uses a Node.js base image , Names this stage "as build", it will install npm dependencies
Copy from Build Stage [COPY --from=build] , will copy the entire output of stage1 /app/build to /usr/share/nginx/html

Final container only has: Nginx server and Static files (HTML, JS, CSS)

👉 Node is NOT present in final image

“Only the final stage is included in the resulting image — previous stages are discarded.”

“Multi-stage build uses multiple FROM statements. The first stage builds the application using Node.js, and the second stage uses a lightweight Nginx image to serve the built files. This reduces image size, improves security, and separates build and runtime environments.”

Difference between CMD and EntryPoint
====================================

vi app.py

import sys

print("App started 🚀")
print("Arguments passed:", sys.argv)


==============

vi Dockerfile

FROM python:3.11

WORKDIR /app
COPY . .

ENTRYPOINT ["python", "app.py"]
CMD ["--env=prod"]


docker build -t myapp .   [Build Docker Image called myapp]

docker run myapp  [Run container from myapp image]

output
----
App started 🚀
Arguments passed: ['app.py', '--env=prod']

ENTRYPOINT → python app.py
CMD → --env=prod

Override CMD
============

docker run myapp --env=dev

output
------
App started 🚀
Arguments passed: ['app.py', '--env=dev']

See the difference:

CMD changed
ENTRYPOINT stayed same

Summary
--------
ENTRYPOINT → fixed command
CMD → default arguments
docker run → overrides CMD

ENTRYPOINT always executes the main application, while CMD acts as default arguments and gets overridden when passing parameters in docker run.”

Docker Security
===============

Docker provides process isolation, but containers are not virtual machines. By default, containers share the host's Linux kernel. If Docker is not configured securely, a compromised container may affect the host or other containers.

The goal of Docker security is to follow the Principle of Least Privilege, minimize the attack surface, and ensure containers run with only the permissions they actually need.


Containers share the same Linux kernel.

Unlike Virtual Machines, Containers DO NOT have their own kernel.

What is Least Privilege?
------------------------
Every application should have only the minimum permissions required to perform its job.

Bad Example: Web Application --> Root Access --> Can modify OS
Good Example: Web Application --> Non-root User --> Limited Permissions

Why? If a hacker compromises the application, they gain access only as appuser instead of root

    Better security

Linux Capabilities
--------------------

Linux divides root privileges into smaller units called capabilities.

Instead of giving a container full root access, give only required capabilities.

Common Capabilities
 ______________________________________________________________
| Capability       | Purpose                                   |
| ---------------- | ----------------------------------------- |
| NET_ADMIN        | Configure network interfaces              |
| NET_BIND_SERVICE | Bind to ports below 1024                  |
| SYS_ADMIN        | Administrative operations (very powerful) |
| SYS_TIME         | Change system time                        |
| CHOWN            | Change file ownership                     |
|__________________|___________________________________________|

1. Why shouldn't Docker containers run as root?
- Running as root gives the application elevated privileges. If the container is compromised, an attacker has more opportunities to perform privileged operations.
- Running as a non-root user reduces that risk.

2. What is the Principle of Least Privilege?
- It means granting users, applications, and containers only the permissions they require—no more and no less.

3. What is Docker Bench?
- Docker Bench for Security is an open-source tool that checks a Docker host and its configuration against security best practices and the Docker CIS Benchmark.

4. What is Docker Scout?
- Docker Scout is Docker's security tool for analyzing images, identifying vulnerabilities (CVEs), comparing images, and providing remediation recommendations.

5. Why should Docker images be scanned?
- To identify known vulnerabilities, outdated packages, and security issues before deploying images to production.

6. Why shouldn't secrets be stored in a Dockerfile?
- Anyone with access to the image can inspect it and retrieve embedded secrets. Sensitive information should be injected securely at runtime.

7. What are Linux capabilities?
- Linux capabilities split root privileges into smaller permission sets. Docker can add or remove these capabilities so containers receive only the privileges they actually need.

8. What is a read-only container?
- A read-only container runs with an immutable root filesystem. The application cannot modify files except in explicitly writable locations such as mounted volumes or tmpfs directories.

9. What are the most important Docker security best practices?

- Run as a non-root user.
- Use trusted, up-to-date images.
- Scan images regularly.
- Protect secrets properly.
- Drop unnecessary capabilities.
- Use a read-only filesystem where possible.
- Keep Docker and dependencies updated.
- Limit CPU and memory resources.
- Avoid running containers with unnecessary privileged options.
